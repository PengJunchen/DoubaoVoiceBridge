# Windows 实机验收与日志回传

本轮开发环境没有 Windows 桌面、豆包 Windows 输入法或 Windows UU 会话。以下为待执行的验收计划。请分别记录本地模拟测试、Windows 原生冒烟、豆包本机听写、UU 跨端粘贴，避免把其中一项的通过当成全部通过。

## 分阶段推进

### A. 程序启动与本机原生接口

1. 完整解压架构对应 ZIP。运行应用，确认托盘、设置和导出诊断按钮可用。
2. 第二次启动应提示已有实例；关闭设置窗口应继续留在托盘，从托盘退出才结束进程。
3. 在有交互桌面的 Windows 源码环境运行 `dotnet run --project windows/tests/DoubaoVoiceBridge.WindowsSmoke -c Release`。保持自己的冒烟窗口前台，过程中不要按键或切换窗口。期待 INPUT 布局、Unicode 剪贴板、自有窗口 Ctrl+V 和剪贴板恢复均通过。非交互或 CI 的前台限制可能使该项失败，需要查明原因；不能直接忽略失败。
4. 原生冒烟只能证明同一进程中的 Win32 基础路径，不能代替后续的豆包或 UU 测试。

### B. 先验证 UU，隔离语音因素

1. 本机复制一段文字，在 UU 远端手动粘贴。若原生 UU 本身不能跨端复制，先解决 UU 配置或连接状态。
2. 在桥接应用绑定真正的 UU 远程桌面窗口，核对确认框的程序名。开启「远控键仅打开测试文字框」，默认关闭自动粘贴、剪贴板恢复。保存。
3. 在远端点选文本框，按 F8。期待只打开本机输入框；输入 `桥接测试 ABC 123 🙂`，并测试包含换行的短段落。点击粘贴，期待回到原 UU 窗口，远端文本出现一次；不应发送消息或出现额外 Enter。
4. Windows 远端先用 Ctrl+V；Mac 远端也先测 UU 默认映射。若无法粘贴，先手动物理按键确认 UU 实际把哪个本机键映射为 Command，再选择 Win+V 或 Alt+V。若打开本机剪贴板历史或本机菜单，该映射不适用，回到 Ctrl+V 并检查 UU。记录每种映射结果。
5. 先测试 1000 ms 同步等待，连续 10 次；如偶发粘贴到上一次文字，增加到 1500、2000、3000 ms，记录最小稳定值。上限 10000 ms。不要通过重复点击补偿，因为结果可能已经投递。
6. 同时开两个 UU 窗口，只应回到触发时的那个窗口。不能将同一窗口内切换远端设备作为已被应用识别的场景；本应用看不到 UU 内部会话 ID。

### C. 手动豆包语音

1. 本机普通文本编辑器先完成一次豆包语音，确认识别、麦克风权限、开始/结束手势正常。
2. 关闭桥接测试模式，保持手动启动方式和自动粘贴关闭。回到 UU 点选远端文本框，按 F8，确认本机框已聚焦；必要时为该本地控件切换到豆包输入法，或者使用已验证的豆包全局语音功能。
3. 亲自按豆包快捷键开始说话，再按其真实停止方式结束录音。等待文字提交，再点击「完成识别」，核对文本后点粘贴。
4. 分别测试短中文、中英混输、数字/标点、长段落、换行、无声、主动取消。观察末尾文字是否完整、有无重复或丢字。
5. 若豆包浮层夺取焦点导致停止或稳定检查失败，记录当时浮层和焦点表现。不要仅增加同步等待；那只影响剪贴板阶段。

### D. 模拟键及自动投递

1. 配置与豆包真实设置完全一致的主键和左右修饰键。默认显示的 Alt+Space 只是可编辑初值，不是对任何版本豆包默认键的保证。
2. 若豆包采用按住说话，选模拟按住；若采用同一组合键分别开始/停止，选模拟切换。UU 前台按住 F8 开始，松开 F8 结束。确认开始和结束都实际发生，录音不会残留。若豆包使用“任意键停止”等不同语义，先用手动模式，不假定切换模式兼容。
3. 若真实豆包快捷键有效、模拟键无效，把该组合标为不支持，回到手动模式并回传日志。软件发出了按键不等于豆包接受了按键。
4. 模拟模式可靠后再开启自动粘贴。每种目标系统连续 20 次短句、5 次长段落；记录识别结束到粘贴时延、丢失末尾、重复、空文本、意外发送次数。
5. 文字稳定判断采用启发式；若豆包停止后仍较晚整理文字，可把稳定等待从 700 增到 1000–1500 ms，最多 3000 ms，仍需验证。无法获得可靠完成信号时保留手动检查。

## 故障和恢复测试

| 操作 | 期待结果 |
| --- | --- |
| 在无关应用按 F8 | 正常传给该应用，桥接不启动 |
| 远控功能键长按产生重复键 | 只开一次会话，无重复粘贴 |
| 极快按下并松开触发键 | 结束请求与启动串行，不留下被按住的模拟键 |
| 在识别时点击其他本机应用 | 停止自动投递，保留文字；不得把新的停止键注入其他应用 |
| 同步等待期间切换到其他窗口 | 取消此次投递，不向新前台窗口粘贴 |
| 同步期间复制另一段文字 | 不覆盖新内容，不继续粘贴旧听写 |
| UU 关闭或重启 | 身份验证失败，保留文字，不向复用句柄投递 |
| 识别没有文字或一直处于组合状态 | 超时保留文本，不自动粘贴半成品 |
| Ctrl/Alt/Shift/Win 尚未松开 | 等待或停止本次操作，不带额外修饰键粘贴 |
| 注入失败 / 权限不一致 | 提示检查结果，日志保留错误码，不自动再次投递 |
| 反复点击粘贴 | 一个会话最多一次注入尝试；不自动重复 |
| 取消 / 正常退出 | 取消后不出现延迟粘贴，尽力释放本应用持有的键 |
| 休眠、锁屏后恢复 | 检查没有残余录音或键状态；失败后取消并重新开始 |
| 修改非法 settings.json 后启动 | 显示配置警告并使用安全默认值；不要默默启用自动投递 |

剪贴板恢复需额外单独验收：普通纯文本可以备份并恢复；图片、文件、自定义格式或超大数据无法安全备份时，应在修改前拒绝此次投递。粘贴后恢复等待期间再复制其他文字，应用必须保留新复制内容。当前快照上限为 8 MiB，支持文本、HTML、RTF、区域设置等字节格式；Win32 多格式恢复若中途遇到系统写入错误不能保证全部格式均已恢复。UU 可能把相同文字重新发布为新代次，此时跳过恢复是正常保护行为。恢复原剪贴板本身可能再次通过 UU 同步，因此默认关闭，开启后应验证不会抢在远端粘贴之前恢复。

## 日志回传

优先使用设置或托盘的「导出诊断 ZIP」。它包含：

- `environment.json`：版本、系统、进程及系统架构、运行时、是否提升权限、日志写入状态。
- `settings-sanitized.json`：快捷键、时延、自动/手动模式、是否已绑定。完整绑定路径被排除。
- `build-info.json`：打包时生成的版本、提交、架构、工作区是否有未提交改动。
- `logs/bridge-*.jsonl`：约 2 MiB 分卷，最多 8 卷，包含 UTC 时间、runId、sessionId、状态转换和错误元数据。

没有记录正文、音频、剪贴板内容、窗口标题、完整程序路径、账号或网络凭证；日志也不是逐键键盘记录。应用本地 `settings.json` 含绑定程序路径，勿以整个数据目录替代诊断 ZIP。不要附敏感听写正文。

回传信息模板：

```text
故障时间（含时区）：
应用版本 / build-info sourceCommit / sourceDirty：
本机系统及架构 / 远端系统：
豆包版本 / UU 两端版本：
触发方式（手动、模拟按住、模拟切换）：
测试文字类别（短中文、中英混合、长句等；无需正文）：
复现步骤：
期望结果：
实际结果（本机有字吗、远端有字吗、重复/丢字/没粘贴）：
复现频率（例如 10 次中 3 次）：
发生时是否切焦点/按修饰键/复制/重连：
诊断 ZIP：
```

分析先按 `sessionId` 关联 `session.begin`、`voice.started/stopped`、`transcript.settled`、`clipboard.staged`、`paste.command_posted` 及错误事件。若已有 `paste.command_posted` 但远端没有文字，重点检查 UU 同步、键位映射和远端焦点；该事件只表示本机成功注入组合键，不是远端回执。若应用无法运行或导出，先保留 `logs/` 文件与版本信息，检查内容后只发送这些文件，不发包含完整设置的数据目录。

## 通过标准

每个受支持组合分别通过 B、C、D 和恢复测试；所有错误投递、意外 Enter、重复投递均必须为零。记录具体版本，不以一台 Windows x64 机器推断 ARM64 或其他 UU/豆包版本。发现不兼容时应明确保留可用的手动方案，或将该组合标为待修复。
